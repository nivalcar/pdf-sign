# 2026-04-19 제네릭 OOP 구조 비교 및 개선안

## 목적

현재 결과와 기대한 방향을 "제네릭을 이용한 동적 처리 구조"라는 기준으로 비교하고, 왜 OOP 기반 전략 구조가 더 적절한지 정리한다.

---

## 현재 결과 평가

현재 구조는 다음 성격에 가깝다.

- 보험 유형을 `union type`과 설정 객체로 정의했다.
- `detectInsuranceType`, `getInsuranceKeyword`, `findAgentAnchor` 같은 유틸리티 함수로 분기 처리를 모았다.
- 타입 체크와 JSDoc 기반 추론으로 안정성은 이전보다 좋아졌다.

즉, 현재 개선은 "타입 안정성 강화 + 설정 중심 분기 정리"에는 효과적이다.

하지만 기대했던 구조와는 차이가 있다.

- 보험 타입별 책임이 클래스 단위로 분리되지 않았다.
- 프로세스가 특정 타입 전략을 주입받아 동작하는 구조가 아니다.
- 제네릭이 "처리 파이프라인의 타입 보장"을 이끄는 수준까지 올라오지 못했다.
- 실제 동작은 여전히 설정 객체와 조건 분기에 의존한다.

정리하면, 현재 구조는 "제네릭 구조"라기보다 "타입이 추가된 함수형 설정 구조"에 가깝다.

---

## 기대 방향 평가

기대한 방향은 아래와 같다.

1. 보험 타입별 클래스를 선언한다.
2. 각 클래스가 탐지 규칙, 기준 키워드, 좌표 계산 책임을 가진다.
3. 처리 프로세스는 구체 타입을 직접 알지 않고, 공통 인터페이스와 제네릭에 의존한다.
4. 새 보험 유형이 추가되면 프로세스 변경 없이 클래스만 추가한다.

이 방향은 확장성 측면에서 더 적절하다.

- 보험 유형별 책임이 응집된다.
- 분기문이 프로세스에서 사라지고 다형성으로 이동한다.
- 타입별 차이를 "데이터"가 아니라 "행동"으로 캡슐화할 수 있다.
- 제네릭은 `Processor<TStrategy>` 형태로 프로세스의 타입 안전성을 유지하는 역할을 맡을 수 있다.

---

## 어떤 구성이 더 적절한가

결론은 명확하다.

현재 구조는 보험 유형이 3개 정도로 고정되고, 규칙 차이도 작을 때는 충분히 실용적이다.  
하지만 사용자가 기대한 "제네릭 중심 구조", "보험 타입별 클래스를 통한 동적 처리", "향후 보험 유형 추가를 고려한 구조"를 기준으로 보면 OOP 전략 구조가 더 적절하다.

판단 기준은 다음과 같다.

| 기준 | 현재 구조 | 기대 구조 |
|---|---|---|
| 타입 안정성 | 좋음 | 좋음 |
| 분기 제거 | 제한적 | 높음 |
| 책임 분리 | 약함 | 강함 |
| 새 유형 확장 | 설정/함수 수정 필요 | 클래스 추가 중심 |
| 제네릭 활용도 | 문서화 수준 | 프로세스 구조 수준 |
| OOP 적합성 | 낮음 | 높음 |

따라서 "제네릭을 중심으로 개선한다"는 목표에는 기대 구조가 더 맞다.

---

## 이번 개선 방향

이번 개편은 다음 구조를 기준으로 진행했다.

### 1. 보험 유형별 전략 클래스

- `LongTermInsuranceStrategy`
- `GeneralInsuranceStrategy`
- `AutoInsuranceStrategy`

각 클래스는 아래 책임을 가진다.

- 자기 보험 유형을 판별하는 패턴
- 기준 키워드
- 페이지 내 앵커 탐색 규칙
- 서명 좌표 계산 방식

### 2. 레지스트리

`InsuranceStrategyRegistry`

- 전체 전략을 보관한다.
- 문서 텍스트를 보고 적절한 전략을 선택한다.
- 미감지 시 fallback 전략을 제공한다.

### 3. 제네릭 프로세서

`InsuranceDocumentProcessor<TStrategy>`

- 어떤 보험 전략이 들어오든 같은 프로세스로 처리한다.
- 프로세스는 구체 클래스가 아니라 공통 계약에만 의존한다.

이 지점이 현재 구조와 가장 큰 차이다.

기존에는:

- `if/else`
- 설정 객체 조회
- 공용 함수 내부 분기

개선 후에는:

- 전략 선택
- 제네릭 프로세서 실행
- 전략별 다형성 적용

---

## 구조적 효과

이번 구조가 적절한 이유는 다음과 같다.

- 보험 유형별 변화 포인트가 한 파일의 한 클래스에 모인다.
- 좌표 계산 규칙이 달라져도 메인 프로세스는 바뀌지 않는다.
- 제네릭은 "아무 전략이나 받아도 같은 프로세스로 실행 가능"하다는 점을 코드 구조로 표현한다.
- 이후 `운전자보험`, `화재보험` 같은 유형이 추가되어도 레지스트리에 등록만 하면 된다.

---

## 결론

현재 결과는 "타입스크립트식 타입 보강"으로서는 괜찮지만, 사용자가 기대한 "제네릭을 활용한 OOP 동적 처리 구조"에는 충분히 도달하지 못한 상태였다.

그래서 적절한 방향은 다음과 같다.

- 설정 객체 중심 구조에서 전략 클래스 중심 구조로 이동한다.
- 공통 처리 흐름은 제네릭 프로세서가 담당한다.
- 보험 유형별 차이는 클래스가 캡슐화한다.

이번 개편은 그 방향에 맞춰 반영했다.
